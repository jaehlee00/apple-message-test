01 / Product choice

Pick how people will open it.

Both paths show the same native components inside Messages. The difference is whether you also want a regular app outside the conversation.

PATH A · MESSAGES ONLY

Standalone iMessage app

People use it inside Messages. You do not need to build a separate Home Screen experience.

Messages app package

Distribution wrapper · no regular app screen

Messages extension

Charts · data · Confirm / Cancel · result

Open ios/StandaloneMessages/ChartMessagesStandalone.xcodeproj

PATH B · APP + MESSAGES

iOS app with an extension

People can open a regular app, or use the shared components inside Messages.

Regular iOS app package

Home Screen app · shared native views

Messages extension

Charts · data · Confirm / Cancel · result

Open ios/AppWithMessages/ChartConcierge.xcodeproj

Separate products, shared code. Both projects use ios/Shared. Neither requires the other project to run. The standalone version still has a packaging wrapper; that does not make it a regular app.

Apple supports both models. Changing a published product from standalone to an extension of a regular app, or the reverse, requires a new App Store app record. Apple’s distribution rules.

02 / A small vocabulary

What these names mean.

Xcode
Apple’s Mac application for editing, building and running iPhone software.
Swift / SwiftUI
Swift is the programming language. SwiftUI describes the native screens. The chart drawing uses Apple’s Swift Charts.
Project
The .xcodeproj file you open. It tells Xcode which source files and settings belong together.
Target
One thing Xcode builds: the app wrapper, normal app or Messages extension. Each has its own settings.
Scheme
A named recipe for building or running targets. Choose it in Xcode’s top toolbar.
Simulator
An iPhone-like test environment on your Mac. It does not establish real AMB delivery.
Bundle ID
A text identifier for a target, such as com.yourcompany.chart.Messages. App and extension have different IDs.
Team / signing
Your Apple development identity and the process that associates the built app with it.
App Store ID
The numeric identity of your App Store product. It is different from the bundle ID and Team ID.
API / endpoint
A server interface and one of its addresses. The app reads data or submits a request there.
Webhook
A server address Twilio calls when something happens, such as an incoming customer message.
AMB / CIM
Apple Messages for Business / Custom Interactive Message. Twilio support for the exact extension message must be verified.

Prepare your Mac and files.

1

Download and unzip the complete package

Extract apple-chart-integration.zip. Keep its folder structure together: the projects reference shared files outside their own subfolders. If you downloaded this guide separately, it does not contain the source code.

Install Xcode and an iOS simulator

Install an Xcode release compatible with your Mac from Apple. Open it once and complete its component installation. Add an iOS simulator runtime if prompted; these projects target iOS 17 or later.

Simulator work comes first. For signed device builds, sign in to your Apple account in Xcode and select the intended team. App Store distribution also needs the appropriate Apple Developer membership and app record.

04 / Separate project walkthroughs

Build the path you want to test.

Show either walkthrough or keep both visible. These controls only filter this guide; they do not change code or Twilio settings.

A · Standalone Messages app

Messages is the user-facing home. The wrapper has no Swift app entry point or regular app screen.

A1

Open the standalone project

In Finder, open ios → StandaloneMessages → ChartMessagesStandalone.xcodeproj. In Xcode’s project settings, find the two targets: ChartMessagesStandalone (wrapper) and StandaloneChartMessages (extension).

Expected: the shared source files appear normally, without missing-file indicators.

A2

Build the package

Select the ChartMessagesStandalone scheme and an iPhone simulator. Choose Product → Build. This scheme builds and archives the package; it intentionally has no normal-app launch action.

Optional Terminal equivalent

Run from the extracted apple-chart-integration folder:

xcodebuild -project ios/StandaloneMessages/ChartMessagesStandalone.xcodeproj \
  -scheme ChartMessagesStandalone -sdk iphonesimulator \
  -configuration Debug CODE_SIGNING_ALLOWED=NO build

The command builds an unsigned simulator product. It does not send a message or install a production app.

A3

Run the extension inside Messages

Choose Product → Scheme → New Scheme and select target StandaloneChartMessages. Run that extension scheme. Select Messages when Xcode asks for a host app; if needed, use Edit Scheme’s Run settings to choose the Messages host.

In Messages, open a test conversation and find the extension in the app menu. Open it with no prior chart message selected. It should load the bundled snapshot and offer the native components.

There is no Home Screen app to open for this path. If Xcode does not offer a Messages host, inspect the scheme and first error instead of selecting the wrapper as a normal executable.

A4

Set path A’s identity for devices

Select each target → Signing & Capabilities. Choose your team on both. Replace the two example bundle IDs with identifiers registered to you. Keep the extension ID under the app wrapper’s ID.

Wrapper example:   com.example.ChartConciergeMessages
Extension example: com.example.ChartConciergeMessages.Messages
Twilio template:   twilio/config/standalone.env.example

For distribution, create this standalone product’s App Store record and add required app/Messages icons, metadata and provisioning. Use its actual App Store ID in Twilio.

B · Regular iOS app + Messages extension

The normal app and extension reuse source code, but they are different processes and entry points.

B1

Open the full-app project

Open ios → AppWithMessages → ChartConcierge.xcodeproj. Its targets are ChartConcierge (regular app) and ChartMessages (extension).

Expected: the app has ChartConciergeApp.swift; the extension uses the shared Messages controller.

B2

Run the regular app first

Select the ChartConcierge scheme and an iPhone simulator, then press Run. This time a regular app opens. Try the component selector and the local mock confirmation.

Optional Terminal build

Run from the extracted package folder:

xcodebuild -project ios/AppWithMessages/ChartConcierge.xcodeproj \
  -scheme ChartConcierge -sdk iphonesimulator \
  -configuration Debug CODE_SIGNING_ALLOWED=NO build
B3

Run the embedded Messages extension

Use Product → Scheme → New Scheme and select target ChartMessages. Run it with Messages as host. Open the extension from a test conversation’s app menu.

Expect the same component choices in a different host. Selection and confirmation state are kept in memory per process; this implementation does not synchronize them with the regular app.

B4

Set path B’s identity for devices

Set your intended team under Signing & Capabilities on both targets. Replace the two bundle ID examples with your registered IDs.

App example:       com.example.ChartConcierge
Extension example: com.example.ChartConcierge.Messages
Twilio template:   twilio/config/app-with-messages.env.example

Use the regular app’s App Store record, its iMessage metadata and its actual App Store ID. Do not use the standalone product’s numeric App Store ID.

Keep the identities separate. If you test both against different servers, build each with its matching public origin. One Twilio environment in this implementation selects one extension identity. App Clip setup is optional and not required for either walkthrough.

06 / Same API, either native path

Connect the hosted snapshot and mock.

1

Install the server tools

On the Mac, install Node.js 22 and the Twilio CLI using the official CLI instructions. In Terminal, go to the extracted package folder. A convenient way is to type cd , drag that folder from Finder into Terminal, then press Return.

node --version
npm test
cd twilio
npm ci --ignore-scripts
npm test
twilio login
twilio plugins:install @twilio-labs/plugin-serverless@4.0.0

The package pins installable dependencies. Earlier backend tests ran on Node 24; verify them on the deployed Node 22 runtime too. Twilio credentials belong in the CLI/environment, never in Swift source or this guide.

2

Choose one identity template

Still in the twilio directory, run one of these commands. This creates your local configuration file; do not overwrite an existing configured file without preserving it.

PATH A
cp config/standalone.env.example .env
PATH B
cp config/app-with-messages.env.example .env

Open .env in a text editor (a leading dot may hide it in Finder). Leave AMB_ENABLE_LIVE_DELIVERY=false. Real identities can be completed before AMB activation; the public snapshot and mock do not need a live outbound message.

3

Deploy the public API to your test service

Confirm the selected Twilio account/profile and intended test service. The next command uploads the Functions and public-company chart assets. It is a real deployment, not a local preview.

twilio serverless:deploy --runtime node22

Copy the HTTPS base origin returned by Twilio. Set PUBLIC_BASE_URL in the chosen environment to that exact origin with no path, query or trailing slash, then redeploy. Keep delivery disabled.

Visit YOUR_ORIGIN/chart-manifest to inspect JSON and YOUR_ORIGIN/chart to inspect the web fallback. Check hosted route visibility: the inbound handler is protected and the contract asset is private. The local development server does not prove hosted signature protection.

4

Point the native build at that origin

In Xcode, open ios/Shared/ChartModel.swift, find ChartConfiguration.publicOrigin, and replace the empty string with the real origin. Keep the quotation marks. Do not paste a URL ending in /chart.

// Shape only — replace with the origin from your deployment:
static let publicOrigin = "https://YOUR_REAL_HOST"

Rebuild and run the selected native project. Confirm now uses the HTTP mock endpoint. It sends a request ID, fixed chart/revision IDs and review action, then displays the returned JSON receipt. Cancel still makes no request. Neither flow changes holdings or performs a real approval.

Insert a component into a consenting test conversation, press Send yourself, and open it on a supported test device. This verifies the native message path separately from Twilio delivery.

07 / Provider integration

Connect AMB only after the contract is verified.

There are public Twilio Communications APIs. The remaining gap is the complete, supported custom iMessage-extension payload and its account-specific setup. The supplied adapter deliberately leaves those fields unverified.

Customer requestAn eligible, customer-initiated AMB conversation
Protected handlerValidate sender + recipient; reserve event once
Provider deliveryVerified envelope → native extension or fallback

The server chooses the extension identity. The app reads its own validated URL and snapshot. Twilio does not upload a running screen from a normal app into the conversation.

1

Ask for the exact channel capability

With your Twilio account team, verify Apple Messages for Business enablement and Custom Interactive Messages invoking your iMessage extension with live layout. Ask for supported standalone/embedded app distribution, App Store ID requirements, send payload, authentication, webhook signatures, replies and delivery callbacks. SMS or rich-link support alone does not answer this.

Use docs/twilio-handoff.md as the detailed checklist and docs/twilio-public-evidence.md for the public documentation already found.

2

Match the product and environment

SettingWhere its value comes from
APPLE_TEAM_IDYour actual Apple developer team.
APPLE_EXTENSION_BUNDLE_IDThe selected path’s extension target in Xcode.
APPLE_APP_STORE_IDThe App Store record for that same product.
PUBLIC_BASE_URLYour deployed origin; must match the native build.
AMB_BUSINESS_SENDERThe documented AMB address for your business.
AMB_TEST_RECIPIENTOne consenting test conversation’s verified opaque identifier. Do not guess a phone-number format.

Keep separate service environments if testing both products concurrently. Each build must use the matching origin and identity.

3

Implement the verified provider mapping

This is the developer review step. Fill twilio/assets/amb-contract.private.json from the actual documentation, recording its reference and review date. Do not set verified=true just to silence an error.

The adapter supports one verified JSON/form request and explicit acknowledgement mapping. If the provider requires multiple requests, another auth method or a different content API, adapt the code to that evidence. The test suite’s synthetic fields are not a Twilio API example.

node --env-file=.env scripts/preflight.cjs
npm test

Preflight currently reports blocked conditions by design. A passed preflight checks configuration completeness; it does not prove delivery.

4

Run one authorized end-to-end conversation

After the supported contract and test recipient are verified, configure Twilio’s documented inbound callback to the deployed protected /amb-inbound route. Enable live delivery in the test environment and redeploy. Have the consenting tester initiate a chart request.

Record each outcome separately: provider acceptance, delivered/failed callback, rendered native bubble, interaction, expanded source data and absent-extension fallback. A returned operation ID is not evidence of a delivered message.

Also verify Confirm, Cancel, retry, duplicate events and mismatched identities. No live message was sent while preparing this package.

08 / Common first-run issues

Find the missing piece.

“I can’t find the standalone app on the Home Screen.”

That is path A’s intended model. Run the extension with Messages as its host and open it from the Messages app menu. Use path B for a regular app screen.

“A source file is red or missing in Xcode.”

Re-extract the full package and preserve the directory layout. Do not move a project away from ios/Shared or ios/MessagesExtension. The paths deliberately share these sources.

“Xcode asks for a team or cannot create a profile.”

Check both targets, the selected Apple account/team and your registered unique bundle IDs. Simulator compilation and signed device distribution are different steps. Keep the full error text if provisioning still fails.

“The standalone scheme won’t Run.”

The supplied wrapper scheme is build/archive only. Create the extension Run scheme for StandaloneChartMessages and use Messages as its host. The regular app’s scheme belongs to path B.

“Confirm says local mock, or Insert is disabled.”

The native public origin is empty or invalid. That is expected during local testing. Set the real HTTPS origin in ChartModel.swift and rebuild for the HTTP stage.

“The received chart shows a network or integrity error.”

Verify the exact origin, fixed revision and deployed manifest. The client intentionally compares it with the bundled snapshot and does not replace a failed fetch with different evidence. Do not weaken that check; deploy the correct preserved snapshot and rebuild as needed.

“Preflight is blocked, or the inbound route returns 503.”

Check the explicit error. An unverified contract, missing identity or disabled live switch blocks sending. Public API hosting can still be tested. Do not copy synthetic test values into production to bypass this.

“My native message works, but Twilio doesn’t invoke it.”

A local/P2P test does not verify AMB capability or its payload. Check the selected product’s App Store ID, extension ID, team, supported distribution, exact provider envelope and delivery events.

“Do I need App Clips, associated domains or a shared App Group?”

Neither selected Messages path requires the optional App Clip setup. No shared login/storage was implemented between app and extension. App Clips remain a separate experiment in docs/app-clip-path.md.
